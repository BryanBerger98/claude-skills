## 1. Need summary

- **Pain**: large multi-domain tasks run as ad-hoc Claude sessions; the chain breaks at every stage (framing, decomposition, execution, verification); more than half of task time is lost to avoidable rework.
- **Current workflow**: ad-hoc Claude Code sessions, no imposed structure; the user describes the need and steers live.
- **Actors**: solo, across all projects (global `~/.claude` install).
- **Frequency**: several large tasks per week.
- **ROI estimate**: >50 % of each task's time recoverable, several times a week → multiple hours/week.
- **Criticality**: high — an uncaught error (bad split, regression, missed spec) can reach production or a client deliverable.
- **Constraints**: moderate token sensitivity (right model per stage, quality over economy); 3 mandatory human gates: after specs, after plan/task split, before delivery; the acolyte-po plugin is reserved for other uses and must not be wired into this workflow (user amendment, 2026-07-13).
- **Scope**: hybrid shape — one common trunk (framing → decomposition) + domain-specialized execution branches (creativity/design/architecture, project management, PM/PO, development, sysadmin/network, DevOps/CI-CD); all component types allowed when justified. User amendment (2026-07-13): granular specialist agents preferred over generalist executors, coordinated through shared standards and templates.
- **Success criteria**: (1) micro-tasks right first-pass (sized, ordered, no missing dependency); (2) execution sticks to the plan without drift on long sessions; (3) nothing delivered without review and tests actually passed; (4) every stage leaves a consultable artifact (specs, plan, tasks, verification report).
- **Candidate loop** (user open to challenge): specs → plan → tasks → implement → review → tests → deliver. Reshaped here: *plan* and *tasks* merge into one decomposition artifact (a plan whose lines ARE the ordered micro-tasks, each tagged with the specialist role that executes it); *review* and *tests* merge into one domain-adapted verification stage; gates sit between stages rather than being stages themselves.

One run: the user (or the `mission-routing` rule) invokes `/mission <big task>`. **Frame** interviews the user — pulling `product-manager`/`product-owner` for product needs and architect advisors for technical shape — and writes `spec.md` into `.claude/docs/missions/<slug>/`; gate 1: the user validates the spec. **Decompose**: `codebase-explorer` recon (code missions), architects contribute constraints, `mission-planner` returns the ordered, **role-tagged** micro-task plan; the parent writes `plan.md` (the persistent task board); gate 2: the user validates the split, optionally after a `grilling` interrogation. **Execute**: mission dispatches each task to the specialist its tag names (`developer`, `devops`, `sysadmin`, `designer`, `product-owner`, `product-manager`…), all preloading `mission-standards`; loaders feed context digests in, nothing raw. **Verify**: `write-tests` dispatches the test writers then runs the suite; the three reviewers apply their lenses (leaning on the built-ins for code); web apps get a `deep-test` sweep; evidence lands in `verification.md`; gate 3: the user approves delivery on that evidence. **Deliver**: commit/create-pr, `github-issues-writer`, `notion-docs-writer`; `gate-guard` blocks delivery commands until the state file reads `verified`.

## 4. Rationale

- **mission (skill)** — the loop is a reusable multi-domain procedure invoked on demand: the skill decision signal, not a subagent (framing dialogue and gate decisions must stay in the parent conversation). Hybrid trunk+branches maps to progressive disclosure: SKILL.md stays small (<500 lines) holding the trunk; each domain playbook is a reference loaded only when that branch runs. Dispatch-by-role-tag replaces the v1 `mission-executor` middle layer: the parent already owns orchestration, so a dispatcher agent would only add a hop and hide routing decisions from the user. Source: <https://code.claude.com/docs/en/skills>.
- **mission-standards (skill)** — the user requires agents to "agree on shared standards and templates"; the documented mechanism is inverse composition: a custom subagent preloads full skill content at startup via `skills:` frontmatter. One skill preloaded by all ~20 agents beats duplicating conventions into 20 system prompts — one source of truth, one place to evolve. Source: <https://code.claude.com/docs/en/skills>.
- **Specialist roster (architects, executors, product, reviewers, test writers)** — official doctrine backs the user's granularity: "each subagent should excel at one specific task", with delegation driven by precise descriptions, least-privilege tool allowlists (omitting `tools` inherits ALL tools — read-only must be explicit), and per-agent model tiering (opus for design/planning judgment, sonnet for scoped execution, haiku for mechanical digests). Two roles from the user's list are arbitrated away rather than built: `project-manager` (splitting, tracking, coordinating and gating ARE the mission trunk — an agent would duplicate the orchestrator) and `qa` (deep-test's qa-api/qa-ui/qa-reporter already execute QA); one role the user's list missed is added: `sysadmin` (system/network administration is one of the six domains; `network-architect` designs, nobody executed). Source: <https://code.claude.com/docs/en/sub-agents>.
- **mission-planner (subagent, extends `planner`)** — decomposition is single-responsibility and context-heavy: isolation keeps recon noise out of the parent, opus fits planning judgment, and emitting the role tag per micro-task is what makes specialist dispatch deterministic instead of improvised. Extending the existing `planner` keeps one planning agent in the setup. Source: <https://code.claude.com/docs/en/sub-agents>.
- **write-tests (skill, finishes the existing stub)** — success criterion 3 ("tests actually passed") is only meaningful if the tests exist: neither `deep-test` (black-box QA on a running app) nor the review built-ins author them. The skill is the procedure (detect gaps, pick layers, run to green); the four writer agents are the specialized authors it dispatches — same trunk/specialist split as the mission itself. Finishing the stub resolves the audit's duplication-risk by construction. Source: <https://code.claude.com/docs/en/skills>.
- **Reviewer trio (security-reviewer, quality-reviewer, specs-reviewer)** — three independent single-responsibility lenses catch failure modes a single generalist review misses; each runs isolated with read-only allowlists and returns evidence to `verification.md`, complementing (not duplicating) the code-focused built-ins by extending the same lenses to non-code deliverables. Source: <https://code.claude.com/docs/en/sub-agents>.
- **I/O agents (notion pair, github pair)** — the digest pattern is the context-isolation signal subagents exist for: raw payloads (Notion blocks, issue JSON) stay in the agent, only compact digests return. GitHub goes through the `gh` CLI (verified installed, v2.91.0) — no server to connect; Notion needs one (below). Loaders run on haiku (mechanical digestion), writers on sonnet (formatting judgment), and writers only persist human-validated content — the same gate-shaped contract the excluded acolyte-po writer had. Source: <https://code.claude.com/docs/en/sub-agents>.
- **notion-mcp (MCP server)** — connecting an external SaaS is the MCP decision signal; acolyte-po's exclusion removes the existing Notion access, so a dedicated connection is required. HTTP transport is the recommended one for cloud services; OAuth runs automatically on 401/403 with `oauth.scopes` pinning for least privilege; user scope (all projects, private) matches the solo-global actor. Declaring it in the two Notion agents' `mcpServers` frontmatter keeps its tools out of the parent conversation entirely; tool search (on by default) defers tool definitions anyway, so context cost stays marginal. `MAX_MCP_OUTPUT_TOKENS` (default cap 25 000) matters for the loader on large pages. Sources: <https://code.claude.com/docs/en/mcp>, <https://code.claude.com/docs/en/sub-agents>.
- **gate-guard (hook)** — with prod/client criticality, gate 3 cannot rest on instructions alone: CLAUDE.md and skill text are "context, not enforced configuration"; a PreToolUse hook is the only deterministic block. Exit code 2 (not 1) is required to actually block, with the reason on stderr fed back to the model. Alternative rejected: a Stop hook fires too late — after the response, not before the delivery command. Sources: <https://code.claude.com/docs/en/hooks>, <https://code.claude.com/docs/en/memory>.
- **mission-routing (rule)** — adoption is the workflow's weakest link (the pain is ad-hoc sessions); a standing rule is the right component for an every-session behavioral nudge, kept to a few lines well under the 200-line CLAUDE.md guideline, specific and verifiable. It routes; it never enforces — enforcement is gate-guard's job. Source: <https://code.claude.com/docs/en/memory>.
- **Duplication-risk resolutions** — `write-tests`: resolved by finishing the stub itself (block above); no competing component is built. `codebase-explorer` plugin-cached copy (acolyte-po): moot for new components since the plugin is excluded from this workflow; every new component references the repo/global agent only. Source for single-source-of-truth practice: <https://code.claude.com/docs/en/sub-agents>.

## 5. Build order

1. **Phase 1 — Trunk online**: `mission` + `mission-standards` + `mission-routing`. Standards come first because every later agent preloads them at authoring time. Payoff: every large task immediately gets framing, a validated split, artifacts, and gates — the four pain points — with verification wired from day one to the built-ins (code-review, verify, security-review), the project test suite, and deep-test, all reused as-is; the rule makes adoption automatic. Effort: L (mission) + S + S.
2. **Phase 2 — Core dev loop**: `mission-planner` + `software-architect` + `developer` (generalize the two existing agents, re-point diagnose to the generalized versions). Payoff: first-pass-correct role-tagged micro-tasks and one-task-per-spawn execution on the most frequent branch — success criteria 1 and 2. Effort: M.
3. **Phase 3 — Verification depth**: `write-tests` + `tests-architect` + the four test writers + the three reviewers. Payoff: authored tests and three-lens evidence behind gate 3 — success criterion 3 at full strength. Effort: L.
4. **Phase 4 — Product branch & delivery I/O**: `product-owner` + `product-manager` + github pair + notion pair + `notion-mcp`. Payoff: PM/PO missions run end-to-end; specs and deliverables flow to Notion/GitHub without polluting the parent context. Effort: M.
5. **Phase 5 — Remaining branches**: `devops` + `sysadmin` + `designer` + `db-architect` + `network-architect` + domain playbooks wiring ultrabrain, audit-my-design, the vercel plugin; register the dormant `grilling` symlink for gate-2 interrogation. Payoff: the six domains reach parity; fills the sysadmin/network gap. Effort: M.
6. **Phase 6 — Deterministic gate**: `gate-guard`. Payoff: gate 3 becomes mechanical, closing the criticality risk; last because it depends on the mission state-file convention stabilizing, while skill-internal HALTs (the proven diagnose/deep-test pattern) hold the gates until then. Effort: S.

## 7. Risks and costs

- **Roster sprawl**: ~20 specialist agents to keep coherent — mitigated by `mission-standards` preloading (one source of truth) and per-family shared templates at build time; still the plan's main maintenance burden. Watch for adherence drift between agents.
- **Token cost**: many spawns per mission; mitigated by tiering (haiku loaders, sonnet executors/reviewers/writers, opus only for planning and design judgment) and by MCP tool search deferring tool definitions. Moderate sensitivity accepted.
- **Routing errors**: a mis-tagged micro-task sends work to the wrong specialist — gate 2 (human validates the role-tagged plan) is the catch point.
- **Enforcement surface**: `defaultMode: bypassPermissions` means gate-guard is the *only* mechanical stop, and its git matcher does not cover deliveries via `github-issues-writer`/`notion-docs-writer` — those stay behind the human gate 3 and the writers' validated-content-only contract; extend the matcher if that proves insufficient.
- **Diagnose coupling**: `planner`/`developer` generalization must keep diagnose green (re-point and re-test it in phase 2).
- **State desync**: gate-guard checks the state file, not reality — verification quality stays human-owned at gate 3. `MAX_MCP_OUTPUT_TOKENS` may truncate large Notion pages in the loader.

## 8. Out of scope

- Slash command — the mission loop needs routing, references, and multi-turn conduct; already covered by the skill type (a bare one-shot transformation is not the need).
- Plugin — solo user, global symlink install; nothing to distribute to a team today.
- Scheduled agent — missions are triggered on demand by the user, never on a clock.
- GitHub Actions / headless — no repository-event trigger in the loop; CI/CD is a *domain the workflow acts on*, not a component of it.
- Agent SDK app — nothing in the loop lives outside the terminal.
- acolyte-po plugin (and its Jira/Notion agents) — user directive, 2026-07-13: reserved for other uses; replaced by the notion pair + github pair + notion-mcp.
- `project-manager` agent (from the user's roster) — arbitrated: splitting, tracking, coordinating and gating are the mission trunk's own job; a dedicated agent would duplicate the orchestrator.
- `qa` agent (from the user's roster) — arbitrated: deep-test's qa-api/qa-ui/qa-reporter already execute QA with scored, evidenced reports; revisit only if non-web QA needs emerge.
